## FB-001 · CLI 工具的"打开浏览器"不走 Duplex —— 已修复

**修复内容（0.2.6 覆盖版）**：
- **A. 候选浏览器注册**（`src/main/browser-registration.ts`）：Windows 下写 HKCU 的 ProgID（DuplexURL/DuplexHTML）+ `RegisteredApplications` + `Capabilities`，让 Duplex 出现在系统"默认应用"列表；**仅打包版执行、只写 HKCU、绝不修改系统默认**；启动 3 秒后异步执行，已注册则跳过。菜单新增「⋯ → 设为默认浏览器…」直接打开系统设置页。
- **B. BROWSER 垫片 + 环境注入**（`src/main/open-shim.ts`）：生成 `~/.cobrowse/shims/duplex-open`（读取 endpoint 调 `POST /api/open`）；面板发起的外部 CLI、内置 agent 的 `run_command` 与脚本执行都注入 `BROWSER=duplex-open` 并把垫片目录置于 PATH 首位。
- **C. URL 入口**：命令行参数 / 第二实例（`second-instance`）/ macOS `open-url` 都会在 Duplex 新标签打开该 URL；新增本地接口 `POST /api/open`。
- **验证**：启动参数开新标签 ✓、`POST /api/open` ✓、第二实例传入 URL ✓（三条实测）；`tests/open-shim.test.ts` 覆盖 URL 解析与 PATH/BROWSER 注入。
- **边界**：忽略 `$BROWSER` 的工具（如 node-open → `start`）仍需用户在系统设置里把 Duplex 选为默认（提供一键入口，不强制）。

<details>
<summary>原始复盘（保留存档）</summary>

**现象**：Claude Code 等外部 CLI 需要打开网页时（OAuth 登录、文档跳转、`vite --open`、`open <url>` 等），一律跳到系统默认浏览器（Chrome/Edge），而不是 Duplex。面板发起的外部工具（Claude/Codex 等）同样如此。

**根因链**（已核对代码）：
1. CLI 打开网页统一依赖操作系统的**默认浏览器关联**：Windows `start`/ShellExecute、macOS `open`、Linux `xdg-open`。
2. Duplex **从未注册为 http/https 处理器，也不是候选浏览器**（`src/` 下 0 处 `setAsDefaultProtocolClient` / 注册表写入）。
3. 面板发起 CLI 时（`src/main/index.ts` 两处 `spawn`：新建会话/续聊）**未注入任何环境变量或 PATH shim**，子进程完全走系统默认行为。
4. Duplex 的 MCP 工具（navigate 等）能开在 Duplex 内，但 CLI **自身**的开浏览行为不经过 MCP，无法拦截。

**已确认的修复方案（D 组合，0.3.0 实施）**：
- **A. 注册为候选浏览器（根治，非流氓原则）**：
  - Windows：HKCU 写 ProgID（`DuplexHTML` 等）+ `RegisteredApplications\Duplex` + `Capabilities`（不修改系统默认、不弹窗骚扰）。
  - macOS：Info.plist `CFBundleURLTypes` + `LSHandlerRank=Default`（候选，实际默认由用户在系统设置选）。
  - Linux：`.desktop` + `mimeapps.list` 候选。
  - 唯一入口：设置里一个"**设为默认浏览器**"按钮 → 深链系统设置页（Windows：`ms-settings:defaultapps`）；卸载时清理注册项。
- **B. 面板子进程注入（兼容不想设默认的用户）**：spawn 时注入 `BROWSER=<duplex-open 启动器>` + 可选 PATH 前置 shim 目录；启动器读 `~/.cobrowse/endpoint.json` 调本地 API 在 Duplex 开标签。
- **C. 接入文档规范**：给外部 AI 的接入说明中写明"打开网页请优先用 Duplex 的 navigate 工具"。
- **子任务 0（先做）**：调研各 CLI 实际打开机制（Claude Code / Codex / Gemini / Qwen：node-open？Rust open crate？是否尊重 `BROWSER` 环境变量），据此确定 B 的覆盖点与优先级。

**涉及文件（预估）**：`src/main/index.ts`（spawn 注入 env）、`src/main/integrations/agents.ts`（plan/env）、`src/main/agent/fs-tools.ts`（run_command env）、新增 `src/main/browser-registration.ts`、设置 UI（Toolbar/设置对话框）、安装器注册项、接入文档。

**验证方式**：
- 设默认后：`cmd /c start https://example.com` 与 `open`/`xdg-open` 落入 Duplex；
- 面板发起 `claude` 的登录流程 → 授权页在 Duplex 打开；
- 不设默认时：尊重 `BROWSER` 的工具落入 Duplex（B 生效）；
- 卸载后：注册项清理干净、系统默认浏览器不被改动。

**待决策点**（实施时确认）：shim 形态（cmd 包装 vs 直接 exe）、Linux 是否纳入 0.3.0 首范围。

</details>

## FB-002 · 模型配置面板点外部应收起（含 Skills 面板）

- 来源：用户反馈（2026-10-11）｜优先级 P2｜状态：**已修（6aa1dc3）**
- **现象**：模型配置面板打开后只能点右上 `»` 或再点 ⚙ 关闭；点旁边空白区无反应（用户预期是弹层式"点外部即收起"）。
- **根因**：`ProvidersPanel`/`SkillsPanel` 是侧栏内常驻块，没有外部点击处理；同类弹层（会话历史菜单）已有 backdrop 关闭先例（`SidePanel.tsx` 的 `.session-menu-backdrop`）。
- **方案**：面板根节点加 `ref` + `window` mousedown 监听；命中范围排除面板自身与对应 ⚙/✦ 按钮（`data-panel-toggle`）。两段式：正在编辑表单时第一次外部点击只取消表单（防误丢未保存内容），无表单时点击即收起；Skills 面板第一步取消"接入 Codex"确认。
- **边界**：浏览器网页内容区是原生视图，点它不触发（只对窗口 chrome 区域生效）。
- **涉及文件**：`SidePanel.tsx`、`ProvidersPanel.tsx`、`SkillsPanel.tsx`
- **验证**：dev 实例 debug 面板脚本（开面板 → 点外部 → 收起；表单打开 → 第一次取消表单、第二次收起）。**2026-10-11 实测 5/5 通过**（含 Skills 面板收起）。

## FB-004 · AI 打开新标签的可见性

- 来源：用户反馈（2026-10-11）｜优先级 P1｜状态：**已修（bd2c83a）**
- **现象**：AI 用 `new_tab` 打开网站后，页面仍停留在当前标签，用户要手动点新标签才看到。
- **根因**：`tool-handlers.ts` 的 new_tab 固定 `{ background: true }`（0.2.9 有意设计，保护人的当前视图），但实际使用习惯要求"打开即展示"。
- **方案（用户已确认）**：默认前台激活；仅当①当前活动标签 2 秒内有真实人工输入（overlay `humanActivity`，源侧已过滤 isTrusted 与 AI 合成输入标记）或②该标签正处于标注模式 → 保持后台，并在结果里附 note 说明。AI 自身动作不会误触发：AI 滚动走 `window.scrollBy`（无 wheel 事件）、输入有 `data-duplex-ai-input` 标记。
- **涉及文件**：`tool-handlers.ts`（new_tab 分支 + `isHumanBusy` 回调）、`index.ts`（`lastHumanActivityAt` 时间戳表）、`shared/tools.ts`（工具描述）
- **验证**：`tests/private-029-smoke.mjs` 新增两条——"new_tab 打开即成为可见活动标签"与"人工滚动期间 new_tab 保持后台"。**2026-10-11 实测 12/12 全绿**。

## FB-006 · 主页磁贴交互与连贯动画（已修复）

- 来源：用户反馈（2026-10-11）｜优先级 P2｜状态：**已修（d4c101d）**
- **现象**：常用网站磁贴遮挡搜索引擎下拉菜单且无法删除（要求：调位置、悬停轻微放大、右上角圆圈 ✕ 点击删除）；随后追加"连贯动画"诉求。
- **根因（遮挡）**：起始页各内容块带入场动画（filter/backdrop-filter），各自形成独立层叠上下文；磁贴区在 DOM 中靠后，整体画在搜索栏内的下拉菜单之上（z-index 只在同一层叠上下文内竞争）。
- **方案**：搜索栏 `z-index:20`、磁贴区 `z-index:10`；磁贴改 `div.shortcut` 包裹（避免按钮嵌套）；悬停上浮+缩放（回弹曲线）、`:active` 按压反馈；✕ 悬停旋转出现，点击先播 160ms 缩退动画再调删除（书签删书签、历史删该条历史），其余磁贴 FLIP 平滑补位（240ms）；引擎下拉开合动画；磁贴入场错峰（35ms/块）。其他界面：面板消息/工具卡入场、查找条下滑入、Toast 出入场、主要按钮按压反馈、工具卡状态过渡。
- **涉及文件**：`StartPage.tsx`、`styles.css`、`App.tsx`；测试垫片补 `useLayoutEffect`（`browser-ui-029.test.tsx`）。
- **验证**：typecheck + 304 单测全绿；dev 实例实测删除补位、菜单开合、两段式面板收起。

## FB-007 · 内置模型"不输出"（partID 覆盖恢复日志）—— 严重，已修复

- 来源：用户反馈（2026-10-11）｜优先级 P0｜状态：**已修（e2cab6c）**
- **现象**："模型对话好像不会输出"：发送后看不到新消息与回答；标注（带提问）也无回复。直觉像模型坏了，实测模型链路完全正常。
- **根因（代码层）**：runtime 的 partID（`u1/a2/t3…`）由内存计数器 `seq` 生成，**应用重启后归零**；而会话 UI 事件日志（`uiEvents`）**跨重启持久化**。重启后的新事件 partID 与旧日志相同 → `pushUiEvent` 的 (kind, partID) 合并逻辑**就地替换旧条目**：新对话被画到列表前部的旧位置、回答被吞或覆盖，用户盯底部看不到任何新输出。`id` 字段早有 `bumpNextId` 跨重启接续处理，partID 漏了同类处理。当日多次重启后集中暴露。
- **修复**：新增 `bumpSeq()`（与 `bumpNextId` 同一模式）：构造与切换会话时，从全部恢复日志的 partID 取最大数字后缀并接续编号；新增回归测试 `continues partIDs after a restored log instead of overwriting it`。
- **影响与残留**：受影响会话的**显示日志**前部有被覆盖的旧条目（LLM 真实上下文/历史完好）；修复后新事件已正确追加。
- **涉及文件**：`src/main/agent/runtime.ts`、`tests/unit.test.ts`、`tests/browser-ui-029.test.tsx`（垫片）
- **验证**：304 单测全绿；dev 实例实测——新消息与回复正确追加在列表底部（修复前会替换到旧位置）。
