## 一、广告拦截

### 1.1 三条路线

| 路线 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 自研过滤器 | `session.webRequest.onBeforeRequest` + 自己解析 EasyList → 匹配 → `cancel` | 完全可控、无额外依赖 | 规则引擎（例外、$domain、正则、CSP 报告）很难做对，性能也难保证 |
| B. 现成引擎 | `@ghostery/adblocker`（MIT，带预编译引擎与 Electron 适配层）驱动 `webRequest` 取消 + 注入元素隐藏 CSS | 规则兼容性好、性能有保证、可离线更新 | 引入一个依赖（体积与供应链） |
| C. 加载 uBO 扩展 | `session.loadExtension()` 装 uBlock Origin | 规则最全 | Electron 只支持**部分**扩展 API，MV3/`declarativeNetRequest` 支持不完整，uBO 属重度扩展，**大概率跑不起来或只跑一半**；需先实测 |

**推荐 B**，并把 C 作为后续"扩展支持"的独立课题（它对密码管理器、翻译同样关键，不该和拦截绑在一起）。

### 1.2 关键工程点（这几条决定成败）

1. **不能拦自己的请求**：Duplex 主进程的 endpoint、MCP、bridge 都是本地回环，必须显式放过（`127.0.0.1` / `localhost`），否则 AI 面板直接连不上。
2. **元素隐藏 vs DOM 移除**：cosmetic 规则必须只做 `display:none`，**不要移除 DOM**——AI 的 `snapshot` / `query` 依赖结构；移除了会让"AI 看到的东西"和"人看到的东西"不一致，破坏共驾语义。反向也要注意：被隐藏的元素仍会出现在 snapshot 里，必要时给工具加 `visible:false` 过滤（现在已经有 visibility 判断）。
3. **per-site 白名单**：拦截必然误杀。必须有"此站关闭拦截"开关，并复用刚做好的站点权限 UI 风格（origin 粒度）。
4. **规则更新**：EasyList 每天变。需要"内置一份 + 定期拉取"，拉取失败回退内置版本。
5. **代理环境**：本机必须走系统代理才能上外网，规则下载也要走 `net`（与续传同样的教训）。
6. **性能**：EasyList 十万级规则。逐条正则匹配会让每个请求都变慢；必须用 token 索引/预编译引擎，且匹配在主进程做——主进程卡住等于整个浏览器卡住。

### 1.3 验收方式

- 20 个真实站点（含视频、新闻、电商）对比：加载完成时间、请求数、是否误杀登录/支付
- 误杀回归：`login` / `oauth` / `pay` 路径白名单必须可一键关掉拦截
- AI 侧回归：`snapshot` 结果与拦截前一致（结构不因隐藏而缺失）

## 二、密码自动填充

### 2.1 现实约束

Electron **没有**内置密码管理器，Chromium 的密码 UI 也不对外暴露。只能自己实现三层：加密存储、表单识别与填充、chrome 侧 UI。

### 2.2 安全红线（先定，再写代码）

1. **Agent 永远读不到凭据**。"AI 在安全范围内可以做一切"——密码不属于这个范围。具体约束：
   - 不注册任何能读出密码的工具（连 `query` 都要继续脱敏，现在已经在做）
   - vault 内容不进镜像事件、不进时间线、不进日志
   - AI 触发的点击**不能**被用来触发自动填充（填充必须由真人手势）
2. **只对精确 origin 填充**：`https://a.example.com` 的密码绝不填给 `http://a.example.com` 或子域；跨源 iframe 一律不填。
3. **存储加密**：`safeStorage.encryptString`（底层走 OS 钥匙串/DPAPI），落盘只存密文。
4. **自动锁定**：超时或系统锁屏后需要重新解锁；解锁态不要持久化。
5. **UI 不能画在页面里**：页面可以伪造任何控件。填充建议放在 chrome（地址栏下方），或至少由主进程控制的 overlay 层。

### 2.3 分期

| 期 | 内容 | 估算 |
| --- | --- | --- |
| P1 | 手动保存（提交密码后询问）+ 同 origin 填充 + 加密 vault | 4–5 天 |
| P2 | 多条凭据选择、旧密码更新、生成强密码 | 3 天 |
| P3 | 从 Chrome `Login Data` 导入（Windows 走 DPAPI 解密，需用户确认）| 2–3 天 |
| P4 | 跨源 iframe 防护、钓鱼提示（origin 与保存时不一致则警告） | 2 天 |

**不建议做的**：让 AI 帮你"登录某个网站"——即使技术上能填，也等于把凭据交给模型上下文。这条要写进产品说明，而不是默默支持。

## 三、UA

### 3.1 精确改法（不要伪造版本）

现状：没有覆盖，页面拿到 Electron 默认 UA，形如
`Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) duplex/0.3.0 Chrome/130.0.0.0 Electron/44.4.5 Safari/537.36`

**只摘掉 `duplex/x.y.z` 与 `Electron/x.y.z` 两个 token，保留真实的 `Chrome/130.x`**：

```ts
app.userAgentFallback = app.userAgentFallback
  .replace(/\s?Electron\/[\d.]+/gi, '')
  .replace(/\s?duplex\/[\d.]+/gi, '')
```

为什么**不要**把 Chrome 版本改高：Client Hints（`navigator.userAgentData`）与真实的 Chromium 能力是同源的，版本号造假会和 `userAgentData.brands` 对不上，反而更容易被判定为伪装浏览器，还可能让站点启用本引擎没有的特性。

### 3.2 风险与开关

- 少数站点会按 Chrome 给全套能力（例如某些 WebGL / 编解码特性），可能触发"特性存在但行为异常"。因此这个开关要能**按站点临时关闭**。
- 回归用第一份的 20 站清单；重点看需要登录的站点（它们对 UA 最敏感）。

### 3.3 顺带能解决的

`Electron/xx` token 是不少站点"识别为非常规浏览器 → 降级/挑战"的直接原因之一。这一条与本轮之前的 ChatGPT 卡顿问题不是同一件事（那是代理），但对"适配性"是实打实的改善。

## 四、建议顺序

1. **UA（30 分钟）**：改动最小、可立刻用 20 站清单回归。
2. **广告拦截（2–4 天）**：先网络层 + 白名单，元素隐藏第二批加。
3. **密码（分期，先 P1）**：安全红线先写进设计文档，再动代码。

三者的共同前置是同一件事：**建一份 20 个真实站点的兼容性回归清单**。没有它，这三个功能都只能靠"感觉没问题"上线。
