# 设计决策：密码管理（导入优先，不做云同步）

> 触发原因：消费级浏览器用户默认会问"它替我记密码吗"。当前状态是**零密码存储**——
> 底层已写好并测试（`src/main/vault.ts`、`src/shared/autofill.ts`），但**没有接 UI 与 IPC**，
> 所以今天不会保存任何密码。这个文件把"接下来怎么接"钉死。

## 一、结论（三条，按优先级）

1. **先做"导入"，不做"保管云同步"**。
   用户最大的痛点是"我的密码都在 Chrome 里"。导入是一次性、可解释、可撤销的动作；
   而云同步是另一个产品的工程量与安全责任。
2. **只做本地加密落盘，密钥在系统钥匙串里**（Electron `safeStorage`）。
   不做自建服务器、不做端到端加密宣传——没做到的事不写在 README 里。
3. **AI 永远读不到凭据**。这条不是承诺，是结构：
   - 工具面不注册任何读取入口；
   - `reveal()` 只在主进程内、由**真人手势**触发的填充路径调用；
   - 填充/列表结果不进镜像事件、不进时间线、不进日志。

## 二、为什么不是"现在就全量接上"

密码是唯一一类"实现错了比不实现更糟"的功能：

- 明文误落盘 → 一次崩溃就可能把凭据写进日志或备份；
- 填充进错 origin → 钓鱼站点拿到密码；
- agent 能读到 vault → 等于把凭据交给模型上下文。

所以顺序必须是：**先做 origin 精确匹配与手势校验（已完成、有测试）→ 再接最小 UI**。

## 三、分阶段

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| P1 | 保存：提交表单后**询问**是否保存；仅当 origin 与表单一致、用户手势触发 | 勾选保存后 `passwords.json` 只有密文；取消则不留痕 |
| P2 | 填充：地址栏下方 chrome 弹层（**不在页面里**），点击后主进程 reveal 并注入 | 子域不填、协议降级不填、跨源 iframe 不填 |
| P3 | 导入：读 Chrome/Edge 的 `Login Data`（Windows 走 DPAPI 解密），导入前显示条数与来源 | 导入后逐条可删；导入失败不影响已有数据 |
| P4 | 自动锁定：锁屏/超时后 `lock()`；解锁需系统认证 | 锁定后 `reveal` 返回 null，UI 可见"已锁定" |

**不做**：云同步、跨设备、浏览器扩展自动填充、让 AI 代填。

## 四、已就绪的底层（可直接复用）

- `src/main/vault.ts`：密文落盘、`reveal` 唯一出口、解密失败跳过单条、origin 规范化。
- `src/shared/autofill.ts`：`canFillInto` 精确 origin、`classifyFields` 识用户名/密码框、`shouldOfferSave` 判断是否该问。
- 两者共 31 条单测，覆盖"落盘无明文""子域不通过""锁定后取不到"。

## 五、发布前必须补的安全项

1. 密钥适配器用 `safeStorage`，**不可用时拒绝保存**（绝不退化成明文）。
2. vault 文件权限 0600（`writeFileAtomic` 已带）。
3. 崩溃/退出时确保不把明文写进 `app.log`（当前日志不含凭据，但新增路径要自查）。
4. UI 必须画在 chrome，不能画在页面里：页面能伪造控件与来源。
